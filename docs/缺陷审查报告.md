审查过程中有两条"看起来很严重"的结论经核实是**误报**，特此记录以免后续被误修：

## 2. P0 详解

### P0-1　`AudioWorker` 读了只存在于 `MainWindow` 上的属性，录音中途静默死亡

**位置**：`app.py:123-127`

```python
if lost > 200 and not self._loss_warned:   # _loss_warned 在 AudioWorker 上不存在
    self._loss_warned = True
    self._loss_total += lost              # 同上
    self._on_loss_warn(lost)              # 这个方法是 MainWindow 的，worker 上没有
```

**为什么会这样**：`AudioWorker.__init__`（`app.py:72-80`）只赋值了 `recorder / segmenter /
transcriber / live_interval / sig / _running` 六个属性。而 `_loss_warned` 和 `_loss_total` 是
`MainWindow.__init__`（`app.py:212-213`）上的实例属性，`_on_loss_warn` 是定义在 `MainWindow` 上
的方法（`app.py:784`）。`AudioWorker` 是完全独立的另一个对象。

**触发路径**：录音中任意时刻出现 >200ms 的音频丢失 → `AttributeError`。
而 `run()` 的 `try`（`app.py:99-137`）**没有 `except`**，只有 `finally`。于是 `finally` 照常执行：
flush 尾段 → `recorder.stop()` → `sig.ended.emit()`。

**后果**：`ended` 信号正常发出，UI 走 `_on_stream_ended` 的正常收尾路径，状态栏显示"已停止 · N 段"。
**没有错误弹窗，没有 traceback**（PyInstaller windowed 构建下 stderr 无处可去）。
用户以为正常录完了，实际从丢帧那一刻起的内容全部丢失。

> 讽刺的是这正是"机器繁忙提示"特性本身要解决的问题——特性存在是为了在丢帧时告诉用户，
> 结果特性自己的代码路径先把录音干掉了。

**项目自己的测试已经抓到了**：`tests/test_startup.py` 的两个结构检查用例失败
（`test_no_dangling_self_calls` 报 `app.py:69 AudioWorker -> ['_on_loss_warn']`，
`test_no_unassigned_attribute_reads` 报 `app.py:127 AudioWorker._on_loss_warn`）。
`build.py:116-119` 因此拒绝构建。**这是当前 HEAD 唯一的红灯。**

**修复方向**：见 §6 第 2 批——不要打补丁补属性，而是完成 `session.py` 重构。
丢帧告警状态本就该属于会话而非窗口，`RecorderSession` 里已有等价逻辑（`session.py:112-120`）。

### P0-2　推理线程每录一次泄漏一条，第二次录音起两条线程并发操作同一个 whisper context

**位置**：`transcribe.py:92-99`（缺保护）+ `app.py:620`（每次录音都调）

```python
# transcribe.py:92
def start(self, on_output: callable, on_error: callable) -> None:
    if self._engine is None:
        raise RuntimeError("模型尚未加载，请先调用 load_blocking()")
    self._stop.clear()
    self._thread = threading.Thread(target=self._run, ...)   # 没有"已在运行就返回"的判断
    self._thread.start()
```

对比 `audio.py:239-242` 的 `MicRecorder.start()`——它是**有**这个保护的。`Transcriber` 漏了。

**为什么会触发**：
- `app.py:620` 在**每次** `start_recording` 都调 `self.transcriber.start(...)`
- 停止录音走 `_on_stream_ended`（`app.py:684-704`），只调 `wait_idle()`，**从不调 `Transcriber.stop()`**
- `Transcriber.stop()` 只在两处被调：切换模型（`app.py:167`、`app.py:187`）和退出（`app.py:1068`）

**第二次录音时的实际时序**：

1. 第一次录音留下线程 T1，仍在 `while not self._stop.is_set()`（`transcribe.py:169`）里循环
2. 第二次录音调 `start()`：`self._stop.clear()`（本来就未置位）→ 建 T2 → **`self._thread = T2`**
3. **T1 的引用被覆盖，但它没有退出**——`_stop` 是清空的，T1 的循环条件继续成立
4. T1 和 T2 同时从 `_final_q` 取任务，同时执行 `self._engine.transcribe()`（`transcribe.py:199`）
5. 两个线程对同一个 whisper `_ctx` 并发调用 `whisper_full`

**后果**：whisper.cpp 的 context 不是线程安全的，这会直接段错误。
同时每次录音泄漏一条 daemon 线程，且每条都在以 30ms 周期空转（`transcribe.py:172`），
在项目明确针对的"老笔记本"上是白烧 CPU。

这直接违反 `transcribe.py:3-5` 自己的模块注释：
> 只有一条推理线程持有 whisper context——…并发调用会直接崩

**为什么测试看不见**：`transcribe.py` 零测试覆盖（见 §5）。

**修复方向**：`start()` 加 `if self._thread is not None and self._thread.is_alive(): return`；
并让 `_on_stream_ended` 在确认队列排空后调用 `transcriber.stop()`，
或把推理线程的生命周期改为绑定到 `Transcriber` 而非每次录音。

## 3. P1 可靠性问题

### 3.1 `stop()` 释放 context 时推理线程可能还在跑（use-after-free）

`transcribe.py:101-108`

```python
def stop(self, timeout: float = 5.0) -> None:
    self._stop.set()
    if self._thread:
        self._thread.join(timeout=timeout)   # ← 返回值没检查
        self._thread = None
    if self._engine:
        self._engine.free()                  # ← 超时了也照样 free
```

15 秒的段在慢 CPU 上跑进 `whisper_full` 很容易超过 5 秒（项目自己的 bench 就用
`wait_idle(180)`，`app.py:1207-1215`）。超时后 `join` 返回 `False` 但被忽略，
接着对正在被读取的 context 调 `whisper_free()` → use-after-free。
触发路径：切换模型（`app.py:187`）、退出（`app.py:1068`）。

**修**：`join` 返回 `False` 时不 `free()`，把释放推迟到线程真正结束。

### 3.2 `wait_idle()` 可能在最后一个任务被取走前就返回

`transcribe.py:176-182` 与 `:152-153`

`_take_task()` 在 `transcribe.py:187` 把任务弹出队列，而 `_run` 到 `transcribe.py:177`
才置 `_inflight = True`。两者之间队列已空、`_inflight` 仍是 `False`，
`busy()`（`transcribe.py:153`）返回 `False`，`wait_idle()` 提前返回。
调用方（`app.py:691`）随即收尾 UI，而最后一句还在解码。

窗口很窄，但这是"丢最后一句话"的经典成因。附带：`_inflight` 的读（`:153`）没加锁，
与写（`:177`/`:182`）无同步关系。

**修**：`_take_task()` 内部即置 `_inflight`，或在出队与置位之间持锁。

### 3.3 GUI 线程被阻塞最长 60 秒

`app.py:690-702`

```python
if self.transcriber:
    self.transcriber.wait_idle(timeout=60)   # 内部是 time.sleep(0.02) 自旋
...
if self.audio_thread:
    self.audio_thread.wait(5000)
```

`ended` 由工作线程 emit、经队列投递到 GUI 线程，所以 `_on_stream_ended` **在 GUI 线程上执行**。
这与 `app.py:664-670` 的注释直接矛盾：

> 这里绝不能阻塞 GUI 线程。…改成只发停止信号，界面复位交给 _on_stream_ended 收尾。

注释描述的正是当前代码没做到的事。等待期间界面不重绘、不能拖动、不能取消。

关闭路径（`app.py:1040-1065`）叠加 8 + 30 + 30 秒，窗口在事件处理中完全死掉且无法打断。

### 3.4 启动时在窗口显示之前同步跑 `nvidia-smi`（最长 5 秒）

`app.py:565` → `device.detect()` → `device.nvidia_present()` → `device.py:53-58`

```python
subprocess.run(["nvidia-smi", ...], timeout=5)
```

`MainWindow.__init__`（`app.py:228`）→ `_check_assets()` → `_start_model_load()`（`app.py:462`）
→ `device.detect()`，而 `main()` 的 `win.show()` 在 `app.py:1237-1238` **之后**。
此时事件循环还没跑起来，`app.py:562` 设置的进度条根本来不及绘制。
用户看到的就是"双击了没反应"，无法区分卡死和慢。

同类调用还有 `app.py:486`。`device.py:128-133` 的 `cpu_hint()` 更狠（8 秒 PowerShell），
只是目前无人调用。

### 3.5 设置保存失败会污染运行中的配置

`settings.py:141-158`

`142-150` 行**就地修改了共享的 live `Config` 对象**，然后才尝试 `save()`。
若 `save()` 抛异常，对话框不关闭（`return`），但 `self.cfg` 已被改脏——
而 `self.cfg` 正是运行中的应用读取的对象。此时点取消，已改的值依然生效。

**修**：改副本，成功后再提交。

### 3.6 应用内下载器从不下载 cudart，CUDA 用户静默退回 CPU

`assetdl.py:26-35` 声明了资产：

```python
"windows": {
    "runtime": "whisper-bin-x64.zip",
    "cuda":    "whisper-cublas-12.4.0-bin-x64.zip",
    "cudart":  "cudart-llama-win-x64.zip",   # ← 声明了
},
```

但 `_fetch_runtime`（`assetdl.py:107-134`）**从头到尾没有读过 `a['cudart']`**。
`grep cudart assetdl.py` 只有这一处声明。

而 `README.md:255` 承诺：
> 并自动补上 CUDA 运行时 DLL（构建包本身不含 cudart，缺了它驱动再新也起不来）

`README.md:493` 又说缺 cudart 会**静默失败**。所以：装 exe 的用户接受下载、
有 N 卡、下载了 CUDA 构建，仍然拿不到 `cudart64_12.dll`，然后静默退回 CPU。

对照 `tools/fetch_assets.py:165-171`——命令行下载器**是**做了这一步的。
两份下载器是完整复制又各自漂移的产物（见 §5.3）。

### 3.7 模型加载没有 generation token，快速切换会装错模型

`app.py:882-890`

`_on_model_loaded` 直接读 `self.loader._current`——一个由 **loader 线程**写、
被 **GUI 线程**读的普通属性，无锁。同时状态栏打印的是 `self.cfg.model`（可能已被改成新值）。
用户快速切换模型 A→B 时，A 的 `loaded` 信号可能装上 B 的对象并报出 B 的名字。

**修**：给每次加载分配序号，只接受当前序号的完成信号。

### 3.8 跨线程直接调方法，违背项目自述的约定

`app.py:677-678`

```python
if self.audio_worker:
    self.audio_worker.stop()      # worker 已 moveToThread 到别的线程了
```

`app.py:6` 的注释说"所有更新都靠 signal 回来"，`Signals`（`app.py:55-66`）里也确实
没有对应的停止信号。当前能跑通只是因为 CPython 的 bool 赋值恰好是原子的。

### 3.9 幻觉过滤词表有两份互相漂移的副本

`whisper_bridge.py:25-39`（`HALLUCINATION_MARKERS`）与 `text_norm.py:128-138`
（`_HALLUCINATION_CJK` / `_HALLUCINATION_EN`）内容大量重叠但不相同，
且**两层串联执行**（`whisper_bridge.py:456` 先滤一遍，`transcribe.py:224` 再滤一遍），
都记到同一个 `dropped_hallucinations` 计数器（`app.py:735`）上，用户无法区分。

更值得注意的是词表内容：`_HALLUCINATION_CJK` 含 `"订阅"`、`"转发"`、`"打赏"`、
`"请大家支持"`，`_HALLUCINATION_EN` 含 `"music"`、`"applause"`、`"www."`。
这些都是**普通词**，用子串匹配会删掉用户真实说的句子。例如口述
"这个频道需要订阅" → 整句被丢弃，而用户只会看到状态栏多了一个"过滤幻觉 1"。

而 `whisper_bridge.py:443-456` 的第一层过滤跑在**未归一化的原始文本**上，
恰恰匹配不到 `text_norm.py:117-125` 注释里说的要处理的繁体输出。

### 3.10 `SAMPLE_RATE` 在四个地方各写一遍

`audio.py:17`、`vad.py:24`、`app.py:51` 各有一个模块级常量，
`whisper_bridge.py:463` 更是直接写裸字面量 `pcm.size / 16000.0`。
`Result.rtf` 由它算出，进而影响 `preview_affordable()` 的判断（`transcribe.py:141`）。
改采样率需要同时改四处，漏一处就会静默算错。

### 3.11 `Config` 是跨线程共享的可变对象

`config.py:14` 是普通可变 dataclass，全项目共用一个实例。
`settings.py:142-150` 从 GUI 线程改它，`app.py:1078-1083` 也从 GUI 线程改它，
`app.py:614-620` 在开始录音时读它。今天安全纯属巧合（恰好都在 GUI 线程），
但这一点**没有任何地方写明**。

另外 `config.save()` 有 5 个调用点、4 种错误策略，其中 `app.py:1080-1081`
是 `except Exception: pass`——保存失败用户完全无感。

### 3.12 `device.detect()` 的结果每次会话跑两遍

`app.py:486`（`_offer_download`）与 `app.py:565`（`_start_model_load`）各调一次，
每次都可能付 3.4 的 5 秒代价。可在 `MainWindow.__init__` 里探测一次并缓存。

## 5. 测试可信度

### 5.1 `session.py` 的 19 个绿色测试保护的是应用不执行的代码

上一个 commit「阶段1：抽出 session.py —— 主干的纯逻辑层」抽出了 `RecorderSession`，
并配了 `tests/test_session.py` 的 19 个用例。但 `app.py` **从未 import 过它**：

```
grep -rn "import session\|RecorderSession" --include=*.py .
  → 只出现在 session.py 自己和 tests/test_session.py
```

`app.py:49` 仍是 `from vad import Segmenter, VADConfig`，
`AudioWorker.run`（`app.py:100-137`）**手写重复了** `RecorderSession` 的全部逻辑：

| `session.py` | `app.py` 的重复实现 |
